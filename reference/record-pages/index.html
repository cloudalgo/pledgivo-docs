    Record Pages Reference#

    The Lightning record pages the package installs. They arrive managed, so you can work in them but not open them in Lightning App Builder — this page is what is on each one, and why.

    How these pages reach your users#

    Each page below is assigned as an app-level default: it takes over the object's record page for anyone working inside the app, and changes nothing anywhere else in your org. A user who opens the same record from Sales or Service sees your own page, untouched.

    Salesforce picks a record page most-specific-first — your own assignment, then the app default, then the org default. Your assignment always wins, so nothing here traps you: if one of these pages isn't what your team needs, build your own in Lightning App Builder and assign it to the app, and it takes precedence from that moment on. You cannot edit the pages below in place, because a managed component belongs to the package that installed it.

    Page layouts do not upgrade

    Most of these pages render their fields through the standard Record Detail component and their related lists through Related Lists, which means the actual fields and lists you see come from the object's page layout, not from the record page. Page layouts install unmanaged — yours to edit, and never overwritten by an upgrade. That is deliberate (your layout customizations survive), but it has a consequence worth knowing: when a package upgrade adds a field, it appears on new installs and not on yours until you add it to the layout. Release notes call out when that applies.

    Standard objects#

    These take over a standard Salesforce object inside the app only. Your Sales, Service and any other app keep whatever record page they already had.

    Campaign Detail#

    Campaign_Detail

    Campaign · RecordPage

    Default in Pledgivo (large form factor)

    Record page for a fundraising campaign — the desk staff run an appeal from. The sidebar carries the live progress card and the embed-code builder; tabs cover event seats, donor-facing questions and FAQs, the story editor, updates, documents and refunds.

    Docs note

    The story editor gets a tab of its own rather than a block inside "Page Content" beside the questions and FAQ pickers. Those two choose which shared records appear; this one is long-form authoring — the admin writes here, previews here, and publishes here, and the editor needs the whole tab's width. Keeping it adjacent to Page Content is deliberate: all three tabs answer "what does the donor read on this page?"

    Updates and documents share a tab but nothing else. They are two independent panels — an update is text a supporter reads, a document is a file a supporter downloads, and neither needs the other to exist — so they are two components, each owning its own rows and its own public-section switch. They sit together here only because an admin who has just finished a milestone tends to write about it and attach the report in the same sitting; splitting them across two tabs would make that one job into two navigations. Kept out of "Page Content", which holds the parts of the page authored once at launch, because these two accumulate over a campaign's life and are visited repeatedly.

    Refund requests get a tab of their own rather than a block under the campaign's fields. On a campaign this panel lists every refund request its donors raised, so it is a queue somebody works through, not a detail of the campaign record — and burying a queue at the bottom of a long detail tab is how requests go unanswered. The full-width main region gives the donor's sentence and the two reply boxes room; the sidebar would wrap them.

    Donation Record Page#

    Donation_Record_Page

    Opportunity · RecordPage

    Default in Pledgivo (large form factor)

    Record page for a donation, adding what the Opportunity fields cannot show alone: a sidebar breaking the gift into its net, processor-fee and donor-covered parts and offering the printable receipt, plus any refund request the donor raised.

    Docs note

    Under the field detail, not in the sidebar: a refund request carries a donor's sentence and two reply boxes, and the narrow column would wrap all three. It sits on the Detail tab (the one that opens by default) so a request waiting on somebody is visible without a click. The panel renders nothing but its own empty state on the gifts that never had a request, which is nearly all of them.

    Donor 360#

    Donor_360

    Contact · RecordPage

    Default in Pledgivo (large form factor)

    Record page for a donor held as a Contact, adding a lifetime-giving summary and the donor's live recurring schedules in the sidebar, plus a printable giving-statement tab.

    Docs note

    The highlights panel is what renders the record's action bar, and the action bar is the only place the layout's platformActionList (Edit/Delete/Clone + Send Portal Access Code) can appear. An empty header region silently swallowed every quick action on this page — the actions were deployed and assigned, just unreachable. Keep a highlights panel here on any record page that is expected to expose a quick action.

    This package's objects#

    Content Template Detail#

    Content_Template_Detail

    Content_Template__c · RecordPage

    Default in Pledgivo (large form factor)

    Record page for a reusable question or FAQ template, pairing the standard fields with a card naming the campaigns that reference it and which of them are showing it to donors right now.

    Docs note

    Record page for Content_Template__c (one reusable donation-form question or FAQ). Exists so the "Where This Is Used" card can sit beside the template's own fields. A template is shared across campaigns, but the reference is a JSON id array on Campaign rather than a lookup, so the platform can build no related list for it and the record otherwise reads as if it belongs to nobody — while editing the prompt silently rewrites it on every campaign pointing here. The Related tab is not empty: Custom_Answer__c does have a real lookup to this object, so the answers donors actually gave to this question list there.

    No action bar. A Custom_Answer__c is a donor's reply captured by the donation form, and its Opportunity__c parent is master-detail — a "New" button here would only ever offer staff a create path that cannot be completed sensibly.

    Fund Detail#

    Designation_Detail

    Designation__c · RecordPage

    Default in Pledgivo (large form factor)

    Record page for a fund (Designation), pairing the standard fields with the Fund Performance card so staff see refund-netted giving, live recurring commitment, and the campaign breakdown alongside the gross Total Raised rollup.

    Docs note

    Record page for Designation__c (a fund/earmark). Exists so the Fund Performance card can sit beside the fund's own fields: the packaged Total_Raised__c rollup on the record is GROSS, while the card reports refund-netted giving, so an admin looking at only the field would over-state a refunded fund. The Related Lists tab surfaces the Donation_Designation__c splits that make up that total.

    Event Attendee Detail#

    Event_Attendee_Detail

    Event_Attendee__c · RecordPage

    Default in Pledgivo (large form factor)

    Record page for a single event seat, pairing the standard fields with a card that shows the tier bought, what the order paid, the rest of the party on that order, and a door control for the seat's check-in status.

    Docs note

    Record page for Event_Attendee__c (one seat at an event). Exists because the only place a seat could previously be acted on was the fundraisers console's check-in board, which is built for a queue at the door and manages seats in bulk. Opening a single seat gave a bare field layout with no way to check it in and no sign of what it cost or who else came in on the same order. The "Seat & Order" card supplies all three, and its door control writes through the same EventCheckInController.setCheckInStatus the board uses — there is no second write path.

    Guest Request Detail#

    Guest_Request_Detail

    Guest_Request__c · RecordPage

    Default in Pledgivo (large form factor)

    Record page for a request raised from the public site. Opens on a plain-language explanation of what was asked and what each verdict does, with the refund, decline, and mark-handled actions; the request's own fields sit behind a second tab.

    Docs note

    Record page for Guest_Request__c. The object's own fields say what the row contains — a type, a status, a JSON payload — but not what a visitor actually asked for, and not what each verdict will do about it. That is what lexGuestRequestDetail is here to say, which is why it is the DEFAULT tab and the field detail is the second one: a reviewer who reads the fields first has already been shown Payload_JSON__c and learned nothing. The panel gates on the request's parent (gift, else campaign), so placing it here does not widen who can see a request — see GuestRequestController.GetRequest.

    Single column (flexipage:recordHomeSingleColTemplateDesktop), unlike every other record page in this package, which uses the header-and-right-sidebar template. This object has nothing to put in a sidebar — no child object points at Guest_Request__c, and feeds, activities and history are all off — so the two-column template reserved a third of the page and painted it blank. The panel is also the widest component the package ships: its metric strip and three verdict buttons sit on one line at full width and wrap badly in a sidebar-width column.

    No Related tab. It rendered permanently empty for the same reason there is no sidebar, and an empty tab reads as a broken page rather than as an absence of data. Add one back if something ever looks up to this object.

    Saved Card Detail#

    Payment_Method_Detail

    Payment_Method__c · RecordPage

    Default in Pledgivo (large form factor)

    Record page for a saved payment method, pairing the standard fields with a card that lists the recurring schedules charged to it and the annual giving at risk if it expires or is removed.

    Docs note

    Record page for Payment_Method__c (a donor's saved card). Exists so the "What Depends On This Card" card can sit beside the card's own fields: Exp_Month__c/Exp_Year__c say when the card dies, but nothing else in the app says what dies with it. The card lists the recurring schedules charged to it — including any matched only on the Stripe token, whose Payment_Method__c lookup is stale — and the annual giving at risk, so the expiry can be acted on before a renewal fails.
