    Code Reference

    Code Analyzer Exceptions#

    Generated 2026-11-28 from a live scan

    This page exists for one purpose: to answer, in writing and in one place, why every Salesforce Code Analyzer finding that this package does not fix is not a defect. It is written for a reviewer who has run the scan themselves and wants to check our reasoning against the code.

    It is generated, not written. A script joins a live scan against a triage file and fails the build in both directions—a new finding with no written justification fails, and a justification whose finding no longer exists also fails. So this page cannot quietly go stale: it is either current or the build is red.

    There are no Critical findings. The remaining High-severity findings are enumerated below with a written reason for each, and none of them is a security defect.

    What this report covers#

    A finding earns an individual written justification here if it is High severity or above, or if it carries the Security tag at any severity. That is the set a security reviewer needs; it is defined in the triage file, not chosen per-run.

    Paths excluded from the scan#

    These are declared, not silent. A reviewer should know what was not scanned and why.

    base/main/default/staticresources/embedWidget.js

    Build output, not source. Generated by node widget-src/build.mjs from widget-src/src/*, minified by esbuild. Findings here are artifacts of minification (mangled names, inlined DOM writes) and cannot be fixed in the file itself. Its hand-written source, widget-src/src, IS scanned: it is a target of the findings ratchet's non-package ESLint run and of its PMD/CPD run (scripts/lint/findings-inventory.py, the three-run scan of 2026-11-28), so the code that becomes this bundle is analysed, only not in its minified form.

    Every finding, and why it stands#

    Stripe.js loaded from js.stripe.com in the two Visualforce payment pages#

    Working as designed · 2 findings · LoadJavaScriptHtmlScript

    What the rule flags. PMD's LoadJavaScriptHtmlScript (AppExchange rule set) flags a <script src> that points at an external host. The review expects JavaScript to ship inside the package as a static resource, so that the code Salesforce reviewed is the code that runs.

    Why it is not a defect here. Stripe.js is the one script that cannot be bundled. Stripe requires it to be loaded from https://js.stripe.com/v3/ at page load and forbids self-hosting, because the library is what keeps card data out of the merchant's origin (PCI DSS SAQ A eligibility) and Stripe patches it in place without a version change. Loading a frozen copy would ship a payment library that is out of date the day it is built. The package confines the load to exactly these two Visualforce pages, which exist only to host the Payment Element in an iframe and to receive the 3-D Secure / bank-authentication redirect; no Lightning Web Component loads any external JavaScript or CSS.

    How to verify. grep -rn 'loadScript' base/main/default/lwc returns nothing; the only loadStyle calls are the five guest-route shells loading the packaged PublicFonts static resource through lightning/platformResourceLoader; and these two pages are the only <script src= markup in the package (lexEmbedBuilder assembles a <script src> snippet as text for an admin to paste on their own site, and loads nothing itself). js.stripe.com is a packaged CSP trusted site. Both pages carry the reason in a comment beside the tag: Stripe's host keeps the integration in PCI SAQ-A scope, /v3/ is Stripe's supported evergreen version, and js.stripe.com is declared to the platform as a packaged CSP trusted site.

    File Line(s) Detail
    base/main/default/pages/stripePayment.page 53 <script src="https://js.stripe.com/v3/"> on the iframe host page for the Payment Element.
    base/main/default/pages/stripePaymentReturn.page 42 Same tag on the 3-D Secure / bank-authentication return page, which must call Stripe.js to read the redirect result.

    What is not in this report#

    The other 130 findings are Moderate, Low and Info style and maintainability rules that carry no Security tag. They are not individually justified because none of them describes a behaviour a reviewer would act on. The largest groups, for completeness:

    Rule Severity Findings
    pmd:ApexDoc Low 71
    cpd:DetectCopyPasteForApex Info 52
    eslint:@salesforce-ux/slds/no-slds-namespace-for-custom-hooks Low 3
    eslint:@salesforce-ux/slds/no-unsupported-hooks-slds2 Moderate 3
    eslint:@lwc/lwc-platform/no-community-import Moderate 1

    The SLDS hardcoded-value rule (no-hardcoded-values-slds2) is not in the table because it is disabled in the analyzer configuration, so none of its hits are counted. Its hits would be the fallback half of the var(--pf-token, value) pattern this package requires everywhere a themeable value appears: the token wins when a campaign sets it, and the fallback renders the intended design when it does not. Taking the rule's suggested fix would replace those fallbacks and break per-campaign theming, so it is a rule this codebase deliberately does not follow.

    What this page does not claim

    A static analyzer is not a security audit, and a clean scan is not a certification. This page states which findings exist and why each one stands—nothing more. The AppExchange security review is a separate process with its own requirements.
