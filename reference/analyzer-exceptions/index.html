    Code Analyzer Exceptions#

    Generated 2026-09-05 from a live scan

    This page exists for one purpose: to answer, in writing and in one place, why every Salesforce Code Analyzer finding that this package does not fix is not a defect. It is written for a reviewer who has run the scan themselves and wants to check our reasoning against the code.

    It is generated, not written. A script joins a live scan against a triage file and fails the build in both directions—a new finding with no written justification fails, and a justification whose finding no longer exists also fails. So this page cannot quietly go stale: it is either current or the build is red.

    Every finding, and why it stands#

    Empty catch blocks in negative tests that assert an exception was thrown#

    False positive · 1 finding · EmptyCatchBlock

    What the rule flags. Same EmptyCatchBlock rule, applied to test code.

    Why it is not a defect here. These are the standard Apex negative-test shape: call the method, and if it does NOT throw, fail. Reaching the catch block IS the assertion passing. The block is empty because there is nothing left to do—the surrounding test already asserts the type and the failure path.

    How to verify. RefundService_Test.cls catches AppException with the companion assertion named in the comment; fflib_QueryFactoryTest.cls catches the expected InvalidFieldException and its very next catch (Exception e) calls System.assert(false, ...) to fail on any other type.

    File Line(s) Detail
    base/main/default/classes/fflib/fflib_QueryFactoryTest.cls 270 Catches the expected InvalidFieldException; the following catch (Exception e) fails the test on any other type.

    Unescaped Visualforce merge field holding the org's own domain#

    False positive · 2 findings · VfUnescapeEl

    What the rule flags. PMD's VfUnescapeEl flags a merge field rendered without HTMLENCODE/JSENCODE, the classic Visualforce XSS vector.

    Why it is not a defect here. {!allowedOrigin} is not user input and cannot be influenced by a request. It is produced server-side by the page controller from System.URL.getOrgDomainUrl()—the running org's own domain—and its only use is as the targetOrigin argument to window.postMessage. An attacker who could set this value would already control the org's domain. Escaping it would be actively harmful: postMessage requires an exact origin string, and an HTML-encoded one would never match, breaking the payment iframe's return channel.

    How to verify. Both pages derive PARENT_ORIGIN from document.referrer first and use the Apex-rendered value only as a fallback, and both refuse to post to the '*' wildcard—the comment above the code says so explicitly. These are the only two packaged Visualforce pages; they exist solely because Stripe.js needs a real page to redirect back to after off-platform 3DS/bank authentication.

    File Line(s) Detail
    base/main/default/pages/stripePayment.page 81 {!allowedOrigin} used as the postMessage targetOrigin fallback when document.referrer is unavailable.
    base/main/default/pages/stripePaymentReturn.page 100 Identical use on the 3DS/bank-authentication return page.

    innerHTML used to paint an Apex-generated QR code#

    Working as designed · 1 finding · @lwc/lwc/no-inner-html

    What the rule flags. The LWC ESLint rule @lwc/lwc/no-inner-html forbids innerHTML, which is the standard DOM XSS sink.

    Why it is not a defect here. The assigned string is not markup from any user or request. It is SVG path data generated procedurally in Apex by QrCodeEncoder—a monochrome matrix rendered as <path> geometry, containing no script, no event handlers, no external references and no interpolated text. It is injected rather than templated because LWC provides no way to build an arbitrary SVG path from a string at render time.

    How to verify. QrCodeEncoder_Test asserts the generated output is script-free. The call site is _paintQrCodes() and is guarded to run once per deck (this._qrPainted), so the sink is not re-entered on reactive updates. The comment above the method records both facts.

    File Line(s) Detail
    base/main/default/lwc/publicThankYou/publicThankYou.js 652 Paints the Apex-generated ticket QR SVG into its slot, once per deck.

    Inner classes with no sharing keyword, where access is decided by the framework base class#

    Working as designed · 2 findings · ApexSharingViolations

    What the rule flags. PMD's ApexSharingViolations flags a class declared without with sharing / without sharing / inherited sharing.

    Why it is not a defect here. These are private inner classes extending a framework base (ControllerAction, GuestAction) whose data access is gated by that framework, not by a class-level keyword. An inner class inherits its caller's sharing context, which is exactly the ambiguity the rule detects—but here it is the intended design: the base class decides, so stating a mode on the inner class would be a behavioural claim rather than a clarification. This is deliberately NOT the same call as the SetupController inner classes triaged separately, where adding the keyword was a genuine no-op that removed ambiguity.

    How to verify. Verdicts recorded in docs/code-analyzer-triage-2026-09-01.md. Guest-reachable data access is enforced in the GuestAction framework and in the selector layer, where FLS and CRUD are asserted centrally (enforceCRUD=true, enforceFLS=true).

    File Line(s) Detail
    base/main/default/classes/donation/controller/DonationMonitorController.cls 63 GetStuckDonations, a private inner class extending ControllerAction.
    base/main/default/classes/fundraising/controller/EventRegistrationController.cls 162 CreateTicketIntent, a private inner class extending GuestAction; its data access is gated by the guest-action framework.

    No sharing keyword on a vendored FFLib class#

    Third-party vendored code · 1 finding · ApexSharingViolations

    What the rule flags. Same ApexSharingViolations rule, on the vendored FFLib Unit of Work.

    Why it is not a defect here. Access level for the Unit of Work comes from whoever constructs it, not from the class itself; a keyword here would not reach the inner SimpleDML class that performs the DML, because inner classes do not inherit the container's declaration. The one place this genuinely matters is already patched and documented as a local fork: SimpleDML is declared without sharing so that guest writes carrying a lookup to a record the Guest License cannot see do not fail at commit.

    How to verify. The class header carries the explanation in a // doc: comment with the Apex Developer Guide citation. The SimpleDML fork is entry 3 of the FFLib fork log in DEPENDENCIES.md.

    File Line(s) Detail
    base/main/default/classes/fflib/fflib_SObjectUnitOfWork.cls 59 The Unit of Work class itself. The inner SimpleDML that performs the DML is explicitly declared without sharing as a documented local fork.

    Configuration.disableTriggerCRUDSecurity() in a rollup domain constructor#

    Working as designed · 2 findings · ApexDangerousMethods

    What the rule flags. PMD's ApexDangerousMethods flags Configuration.disableTriggerCRUDSecurity(), which turns off FFLib's own CRUD assertion inside the trigger layer.

    Why it is not a defect here. The FFLib domain layer re-asserts isCreateable() on every record even when the DML is running in SYSTEM_MODE, which makes an internally-triggered rollup fail for any user who cannot directly create the rolled-up record. These two domains recompute totals only—Designation__c and recurring-donation aggregates—and the call scopes the opt-out to the FFLib trigger check alone. The DML itself still runs under the platform's rules; the platform's own CRUD, FLS and sharing enforcement is untouched. Without it, a non-admin donation write silently stops rolling up fund totals.

    How to verify. Both call sites are annotated in place. In RecurringDonations the call sits behind an explicit suppressTriggerCrudCheck flag rather than being unconditional. The wider reasoning—that field permissions are inert without object access on a master-detail detail object—is written up in the Change Management section of AGENTS.md and in the EventTicketTypesSelector class header.

    File Line(s) Detail
    base/main/default/classes/donation/domain/DonationDesignations.cls 25 Designation total rollup. Without the opt-out the rollup silently stops recomputing fund totals for non-admin users.
    base/main/default/classes/recurring/domain/RecurringDonations.cls 40 Same call, behind the explicit suppressTriggerCrudCheck flag rather than unconditional.

    Style and performance findings inside vendored FFLib#

    Third-party vendored code · 40 findings · ApexUnitTestMethodShouldHaveIsTestAnnotation, EagerlyLoadedDescribeSObjectResult, OverrideBothEqualsAndHashcode

    What the rule flags. Findings in base/main/default/classes/fflib/ — an eagerly-loaded describe result, test methods without @IsTest, and one class overriding equals without hashCode.

    Why it is not a defect here. This directory is a vendored copy of the upstream apex-common and apex-mocks libraries, not code this package authors. It is vendored rather than taken as a package dependency so that a subscriber installs one thing instead of being forced to install FFLib into their Dev Hub first. None of these findings is a security issue or a defect: they are upstream style choices and a describe-loading preference. Patching them would fork the tree further from upstream for no functional gain, and every future upstream sync would have to re-apply them. The four patches that ARE load-bearing are patched, and each is logged.

    How to verify. The vendored tree was synced to upstream master on 2026-09-01 (apex-common 485d3046, apex-mocks 6889cc05), closing roughly 1,500 lines of drift, with exactly four local patches re-applied on top. Every one of those four is recorded with its reason in the FFLib fork log in DEPENDENCIES.md.

    What this page does not claim

    A static analyzer is not a security audit, and a clean scan is not a certification. This page states which findings exist and why each one stands—nothing more. The AppExchange security review is a separate process with its own requirements.
