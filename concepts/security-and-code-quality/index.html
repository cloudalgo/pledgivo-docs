    Core Concepts

    Security & code quality#

    Every pull request into this package is scanned with Salesforce's own Code Analyzer. This page publishes what the latest scan found — including the findings that are still open — because a number you can check is worth more than an assurance you can't.

    The short version#
    Critical findings 0 — and 0 on every scan to date
    Known-vulnerable JavaScript libraries 0 — RetireJS returns nothing across the shipped package
    Card data stored in Salesforce None. Stripe.js tokenizes in the browser; only a payment-method ID reaches Apex
    Public inbound endpoints None. Salesforce asks Stripe for payment status — nothing is pushed into your org
    API secrets in package fields None. Stripe keys live only in a Named Credential your admin creates
    Apex test coverage (packaged version) 95%, measured by Salesforce, against a 75% requirement

    What removes risk before a scanner sees it#

    A static analyzer can only find problems in code that exists. Four architectural decisions mean large categories of them are never written in the first place.

    No cardholder data ever reaches your org. The donation form loads Stripe's Payment Element, and the card is tokenized in the donor's browser. What Apex receives is an opaque payment-method identifier. There is no field on any object in this package that could hold a card number, and nothing to leak if a record is over-shared. See Donations & payments.

    No inbound webhook, so no public endpoint. Most payment integrations register a URL that the processor calls back into. This one inverts that: after a donor pays, a scheduled job in Salesforce asks Stripe what happened. There is no exposed endpoint to secure, no webhook signing secret to store or rotate, and no unauthenticated write path into your data.

    Secrets are never packaged. The package ships no API key, in a custom field or anywhere else. Your admin creates a Named Credential during setup and Salesforce holds the key; the package references the credential by name. See Connecting Stripe.

    The guest user can only insert. The public donation and event pages run as the Experience Cloud guest user, which in this package is granted the narrowest set of permissions the flow demonstrably needs. A guest submission is written as a staging row and picked up by a background job running in an authenticated context — a guest cannot create a Contact or an Opportunity, and cannot read one back.

    The whole repository, counted to the finding#

    The table above is the gate, and it stops at base/. A second scan, the findings ratchet, covers everything the repository ships or builds with: the package, the embed widget source, the marketing site and the repository's scripts. It runs the analyzer three times (every engine except ESLint over all four places, then ESLint twice, with and without the Lightning Web Components rule set) and merges them into one count. Today that count is:

    Findings
    Real findings 197
    Raw findings 493
    Deliberate lint fixtures 296

    The fixtures are bad code on purpose: each one proves that a lint in the repository still fires when it should. They are counted separately, never fixed, and never part of the real total.

    Sprint 6B set out to burn the real count down. It started at 556 real findings (850 raw, 294 of them fixtures) and stands at 197 on main today. The ratchet is what keeps it there: every rule has an exact budget, so a rule above its number fails the pull request and a rule below its number fails too, which forces each fix to lower its own number. No suppression can be added to make a count fall, because every kind of suppression has a number of its own and the list of what each one covers may only shrink. Every engine has to have run, and each run's list of applied rules may only shrink. The full mechanism is described under How it stays this way.

    The 197 real findings, by rule:

    Rule Findings Where Status
    ApexDoc 82 Test classes and test helpers only Deferred until the test-suite trim lands, so the work goes only to the tests that stay
    DetectCopyPasteForApex 79 77 in test code, 2 in the framework The 77 wait for the test-suite trim. The 2 are an owner decision, below

    Every remaining finding is either being fixed in an open Sprint 6B task or is a recorded owner decision. None is left behind for style. The decisions:

    • The two Stripe.js findings. Stripe requires its script to load from js.stripe.com, never bundled or pinned, for PCI reasons. This is the one external script in the package and the one exception to the rule that nothing external loads. It runs in a Visualforce iframe that holds no Salesforce session.
    • The framework's two copy-paste findings. The with sharing and without sharing runners in the framework's Dml and Query classes differ only by the sharing keyword, and the keyword is the behaviour: a runner that does not declare its own keyword would silently inherit its caller's. The analyzer counts the duplication; it cannot be removed without removing the guarantee, so it stays counted rather than suppressed.
    • pfSitePath's @salesforce/community import. The platform requires that import to resolve a site's base path, and the Apex alternative reintroduces a bug the import fixed. It stays as a counted finding.
    • The three SLDS 1 styling hooks in uiDialogStyles.css. SLDS 2 has no equivalent for them, and keeping them means orgs still on SLDS 1 render the dialogs exactly as before. Each hook is reported by two rules, which is why three hooks appear as six findings.

    Rules that are switched off, and why#

    Five rules are disabled in code-analyzer.yml, each with its reason written next to it. None is a security rule, and none runs under the AppExchange + Recommended:Security selectors the AppExchange reviewer uses. The counts below are what each rule reports when it is switched back on, measured on base/ in the same scan:

    Rule Findings when enabled Why it is off
    slds/no-hardcoded-values-slds2 12,673 Asks for every literal CSS value to become an SLDS styling hook. This package styles with its own --pf-* tokens, where the literal is the fallback half of the var(--token, value) pattern: a campaign's own branding wins when it sets a token, and the intended design renders when it doesn't. The rule cannot be satisfied without giving up theming, and its auto-fix would break every campaign that overrides a token.
    ApexUnitTestClassShouldHaveRunAs 2,517 Reports every test method that doesn't wrap itself in System.runAs: one finding per method, none in shipped code. Tests whose result depends on who is running them (CRUD/FLS, sharing, guest access) already run as a constructed user.
    MethodNamingConventions 2,727 Rejects the test_thing_doesThing naming the whole test suite uses on purpose. Replaced by a retuned copy of the same rule, below.
    ApexUnitTestClassShouldHaveAsserts 45 Only recognises System.assert* and Assert.*, not this repository's named assertion helpers. Replaced by a retuned copy, below.
    EmptyStatementBlock 115 Flags empty bodies that the language or the architecture requires. Replaced by a retuned copy, below.

    Three rules are measured against this project's conventions, not PMD's defaults#

    code-analyzer.yml switches off the last three rules above and re-registers each one through a custom ruleset (scripts/lint/pmd/pledgivo-conventions.xml) so that it tests what it is meant to test:

    • MethodNamingConventions is retuned to this project's testPattern, so the deliberate test_thing_doesThing convention passes while a badly named production method is still reported.
    • ApexUnitTestClassShouldHaveAsserts is widened to accept this repository's named assertion helpers (assert*), which carry the assertion for whole families of tests, for example the framework's own doubles (UnitOfWorkFake, Mock, Query.executed). A test that calls neither an assertion nor a helper is still reported.
    • EmptyStatementBlock is retuned to skip the shapes the language or the architecture requires: overrides of a deliberately abstract hook, methods of a class that implements an interface, virtual hooks, private no-arg constructors, and a no-arg constructor beside another constructor. It still reports every empty if, loop or plain method.

    On this tree the three retuned rules report nothing, so none of them appears in the 197. They are still enforcing: a method named badly and a test that neither asserts nor verifies are both still reported. That was checked against a deliberately bad fixture rather than assumed, because a mis-registered custom rule and a correctly-registered one look identical on a clean tree — both produce zero findings.

    Every security-tagged finding, and what it is#

    The analyzer tags 2 findings across the whole package as security-relevant (scan of 2026-11-28, AppExchange + Recommended:Security rule selectors — the same command the AppExchange reviewer runs). Both are listed here with a verdict, and both are also recorded in the project's triage record and annotated in the code itself.

    Severity Rule Where Verdict
    High LoadJavaScriptHtmlScript stripePayment.page, stripePaymentReturn.page The one external script the package loads is Stripe.js, which Stripe requires to be loaded from js.stripe.com and never bundled or pinned, for PCI reasons. It runs in a Visualforce iframe that holds no Salesforce session.

    Findings that used to appear in this table are gone rather than justified: the ApexDangerousMethods and ApexSharingViolations entries, which came from a vendored library's trigger CRUD check and Unit of Work and went when the package's own framework replaced it, the ticket page's innerHTML write (the QR code is now a template-bound <svg> path, so there is no DOM sink at all), eight credential-shaped identifier names that were renamed to say what they actually hold (a Named Credential endpoint, a setup-checklist label, an email closing), and the 17 ProtectSensitiveData findings. That rule reads nothing but a custom field's API name, and matched substrings such as Sign (in Designation), Cred (in Credit), Token, Key and Hash. Each field was renamed before the first release to say what it holds: the fund lookups are Fund__c, the two Named Credential name fields are Stripe_Donor_Callout_Name__c and Stripe_Admin_Callout_Name__c, the portal's SHA-256 fields are Code_Digest__c and Session_Digest__c, and the checkout's capability token is Checkout_Capability__c. Their labels and descriptions still use the plain words ("Access Token", "Code Hash"), so an admin reading a field still sees what it is.

    These two are the only High findings left. The 20 others that the September scan reported were none of them security-tagged: every one was inside a vendored third-party library that this package carried as source and has since removed.

    Every one of them is written up individually. The package publishes a Code Analyzer exceptions report listing each finding it does not fix, what the rule flags, why it is not a defect here, and how to check that for yourself against the code. That page is generated from a live scan rather than written by hand, and the build fails if a new finding appears without a justification or if a justification outlives the finding it explains — so it cannot quietly go out of date.

    The submission documents#

    The two write-ups uploaded with the review are published here as pages, rendered from the same HTML the PDFs are printed from, so neither can drift from what Salesforce was sent:

    • Solution architecture: what the package is made of, how a donation moves through it, where data lives, and what is reachable from outside.
    • Sample API callouts: every outbound request to Stripe with sample bodies, and the one inbound REST endpoint the package exposes.

    The false-positive documents#

    Salesforce's review process expects a written response to every finding a partner does not fix, from both scanners it runs. Both responses are published here, and this is their only copy — the same files are what the submission uploads, so a reviewer reading the site and a reviewer reading the submission see the same document.

    Scanner What it answers Document
    Force.com Source Code Scanner (Checkmarx), run through the Partner Security Portal on 2026-10-07 All 273 reported security paths, grouped by rule and resolved to the 91 code locations they point at, and a disposition for each of the 100 code-quality paths PDF · XLSX
    Salesforce Code Analyzer, AppExchange + Recommended:Security (the command in The latest scan) Every finding in the table above, one response each, joined from the same triage record CI enforces. Each response states the scanner's claim in its own words, why that claim is false at that site, the supporting detail, the evidence to check against the code, and the sources it relies on PDF · XLSX

    Both PDFs follow the False Positive Documentation template Salesforce's security team gives partners: the application, package and version, partner and filing date once, then the template's four questions — vulnerability name, detected by, detailed explanation, evidence — repeated once per finding (one per flagged code location for Checkmarx, one per reported finding for Code Analyzer), with the box the Salesforce reviewer fills in left blank under each one. The explanation has a fixed shape: the scanner's claim (the rule's own description and the statement it points at), one paragraph stating why that claim is false for this statement, the supporting detail, and the Salesforce or vendor documentation each reason rests on; the evidence gives the flagged code (for Checkmarx, the dataflow the scanner reported as well) and what was checked. An appendix records the scan itself and indexes every raw finding to its entry; the Checkmarx one also gives the code-quality paths their dispositions. Each spreadsheet holds the same responses as rows, for anyone who prefers to filter.

    They are built, not written: a script in the repository turns the scan output and the triage record into the PDF and spreadsheet, so when a finding is fixed or a verdict changes the document is regenerated from source rather than edited by hand.

    What this page does not claim

    Code Analyzer is a static analyzer, not an audit, and a clean scan is not a security certification. This package has not completed Salesforce's AppExchange security review; when it does, that will be stated here as a separate fact. What the numbers above establish is that the code is scanned continuously, that the findings are published rather than filtered, and that every security-tagged one has a written verdict.

    How it stays this way#

    The scan is a required check on every pull request into the main branch, and runs again weekly so that a rule added in a new analyzer release surfaces against unchanged code.

    • A Critical finding fails the build. The budget is zero, and the package has never had one, so any Critical is a genuine regression rather than an accepted baseline.
    • High findings are capped at the current count. A pull request that adds one fails. Raising the cap is a deliberate, reviewed act that has to arrive with a written verdict for the new finding — it can't be nudged up to turn a build green.
    • Every finding count is held to an exact number. A second scan covers the package, the embed widget source, the marketing site and the repository's scripts (the weekly Graph Engine job is separate) and compares the count of each rule with scripts/lint/findings-budget.json. It is three analyzer runs merged into one count: every engine except ESLint over all four places, ESLint over the package with the Lightning Web Components rule set, and ESLint over the rest (the widget source, the marketing site, the scripts) with that rule set switched off, because those files are not Lightning Web Components. The second configuration is generated from the first and the check fails unless the two differ in exactly that one setting. Switching the Lightning rule set off also takes 23 other ESLint rules out of that third run, which is a decision and is written down: the four import/* rules (the widget's esbuild build and the marketing site's Astro build already reject an import that does not resolve), the 18 jest/* rules (the repository has no Jest), and @salesforce/lightning/valid-apex-method-invocation (it only applies to Lightning Web Components). The rule list each run really applied is read from the analyzer's own log and written out, sorted, in the budget file, and must match it exactly; against the main branch, a rule that a run used to apply and no longer does fails the check by name, while an added rule does not, so a plugin upgrade that drops a rule fails loudly. The merge never counts a finding twice (a finding that two runs both report fails the check), each run has to show that its engines ran on the targets it is defined to scan and that its own log is complete, and a report or log is tied to its run by file name. The analyzer's ESLint configuration is expected to be plain data, and a check of its text acts as a tripwire for accidental reads of the engine's state (it is not a proof, since a text check over JavaScript can never be complete); the rule list above is the real control. One case the list cannot see is a configuration computed inside the engine that turns a rule off for some files only while the rule stays on elsewhere, so a change to that file is reviewed by a person. A rule above its number fails the pull request, a rule that is not in the file has a number of zero, and a rule below its number fails as well, so a fix lowers its number in the same pull request and a narrowed scan cannot pass as progress. Copy-paste is counted in duplicated lines, and every kind of suppression (inline markers, including the analyzer's own, ESLint rules turned off or ignored, the analyzer exceptions, and the ignores, bulk suppressions and disabled rules in the analyzer's own configuration) has a number of its own, so none can be added to make a count fall. What each suppression covers is written out as an explicit, sorted list in the same file, and a suppression may only shrink in a pull request, never grow: any entry the main branch's list does not have fails the build as a new or widened suppression, so widening a file pattern or swapping the rule it covers cannot pass. The analyzer's engine settings (and the content of the rulesets they name) and the ESLint options are hashed into a number, so changing a knob such as the copy-paste detector's minimum size or loosening a ruleset shows up as a budget change in the pull request instead of passing silently. The scan also fails if an analyzer engine did not run, if its log cannot be recognised, or if an engine could not read a file that is not on the recorded list. Such a file is fixed so the engine can read it, never added to the list: the usual causes are a #! line or non-ASCII punctuation in a .mjs file (the copy-paste detector cannot read them) and an optional catch { binding (the analyzer's JavaScript parser for PMD cannot). A pull request cannot raise a number above, or drop a key from, the budget on the main branch; a changed hash is flagged with a warning on the pull request (engine settings do change legitimately) and has to be explained in its description. Deliberate lint fixtures, which are bad code on purpose to prove that each of the repository's own lints fires, are counted separately and never fixed.
    • The analyzer version is pinned, so a red build always means new code, never a new rule quietly appearing.
    • Auto-fixes are never applied wholesale — the SLDS rule above is the reason.

    Alongside it, a separate workflow audits the package's shipped JavaScript dependencies weekly and on every pull request, and fails on any advisory at any severity.

    Test coverage#

    145 Apex test classes and over 2,300 test methods ship inside the package. Salesforce recomputes coverage itself when a package version is built and refuses to release one below 75%; the current version measured 95%.

    Coverage is also verified across account models a development org can't reproduce. Before a version ships, the same packaged build is installed into four separate orgs — standard Contact/Account, Person Accounts, NPSP, and Person Accounts with NPSP — and the full test suite, a set of probes that push real records through the real packaged triggers, and the browser-level donation flow are all run in each. Results are diffed against the standard-account org, so a difference that only appears under Person Accounts or NPSP is visible instead of being buried in noise common to all four.
